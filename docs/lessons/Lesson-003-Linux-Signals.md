## 2. Signal Definition

A signal is an asynchronous notification delivered to a process.

Asynchronous means that the signal may arrive independently of the normal program flow.

A program may be executing:

```c
applicationUpdate();
```

when a signal arrives.

The kernel may then temporarily interrupt the normal flow and apply the configured signal behavior.

A signal mainly communicates:

```text
An event has occurred
```

It is not intended to be a general-purpose data-transfer mechanism.

---

## 3. Signal Sources

Signals may be generated by several sources.

### Terminal Input

Pressing:

```text
Ctrl+C
```

usually causes the terminal driver to send:

```text
SIGINT
```

to the foreground process group.

### Another Process

A process can request that the kernel send a signal using:

```c
kill(targetProcessId, SIGTERM);
```

### The Kernel

The kernel may generate signals for events such as:

* Invalid memory access
* Illegal instruction
* Arithmetic fault
* Child process termination
* Timer expiration
* Broken pipe

Examples include:

```text
SIGSEGV
SIGILL
SIGFPE
SIGCHLD
SIGALRM
SIGPIPE
```

### The Process Itself

A process can send a signal to itself using:

```c
raise(SIGTERM);
```

or:

```c
kill(getpid(), SIGTERM);
```

---

## 4. Signal Lifecycle

A signal can be described using three stages:

```text
Generated
   |
   +-- Pending
   |
   +-- Delivered
```

### Generated

The signal is created.

Example:

```bash
kill -TERM 1180
```

### Pending

The signal is waiting for delivery.

This can happen when the signal is temporarily blocked.

### Delivered

The kernel applies the configured signal behavior.

The process may:

* Apply the default behavior
* Ignore the signal
* Execute a registered signal handler

---

## 5. Signal Disposition

The configured behavior for a signal is called its disposition.

The three common dispositions are:

### Default Behavior

```c
SIG_DFL
```

The standard Linux behavior is applied.

For example, the default action for `SIGTERM` is process termination.

### Ignore

```c
SIG_IGN
```

The process ignores the signal.

Example:

```c
signal(SIGTERM, SIG_IGN);
```

### Custom Handler

A user-defined function is executed.

Example:

```c
signal(SIGTERM, terminationSignalHandler);
```

or preferably:

```c
sigaction(SIGTERM, &action, NULL);
```

---

## 6. Signals That Cannot Be Handled

Two signals have special behavior:

```text
SIGKILL
SIGSTOP
```

These signals cannot be:

* Caught
* Ignored
* Blocked
* Assigned a custom handler

The kernel always retains control over them.

This ensures that a process cannot make itself impossible to terminate or stop.

---

## 7. The `kill()` Function

Despite its name, `kill()` does not always terminate a process.

Its purpose is to send a signal.

Prototype:

```c
int kill(
    pid_t pid,
    int signalNumber);
```

Example:

```c
kill(targetProcessId, SIGTERM);
```

This means:

```text
Ask the kernel to send SIGTERM to the target process
```

The target process may:

* Terminate
* Run a handler
* Ignore the signal
* Delay delivery while the signal is blocked

Therefore, successful return from `kill()` does not guarantee that the target process has terminated.

---

## 8. `kill()` Return Value

The `kill()` function returns:

```text
0  › Signal request accepted successfully
-1 › Failure
```

On failure, `errno` is set.

Possible errors include:

* Target process does not exist
* Permission is denied
* Invalid signal number

Example:

```c
if (kill(targetProcessId, SIGTERM) != 0)
{
    perror("kill");
}
```

---

## 9. Special PID Values in `kill()`

The PID parameter changes the target behavior.

### Positive PID

```c
kill(1180, SIGTERM);
```

Sends the signal to process `1180`.

### PID Equal to Zero

```c
kill(0, SIGTERM);
```

Sends the signal to processes in the caller's process group.

### PID Less Than Minus One

```c
kill(-2000, SIGTERM);
```

Sends the signal to the process group whose ID is `2000`.

### Signal Number Zero

```c
kill(targetProcessId, 0);
```

Does not deliver a real signal.

It can be used to check:

* Whether the process exists
* Whether the caller has permission to signal it

---

## 10. `SIGINT`

`SIGINT` means:

```text
Interrupt signal
```

It is normally generated when the user presses:

```text
Ctrl+C
```

The terminal driver sends `SIGINT` to the foreground process group.

The default behavior is process termination.

A process may install a handler and perform graceful shutdown instead.

On Linux, the common signal number is:

```text
2
```

Observed output:

```text
^C[APPLICATION] Received signal: SIGINT (2)
```

The `^C` text was displayed by the terminal.

---

## 11. `SIGTERM`

`SIGTERM` means:

```text
Termination request
```

It is the standard signal used to request a controlled process shutdown.

It can be sent using:

```bash
kill -TERM PID
```

The default `kill` command also sends `SIGTERM`:

```bash
kill PID
```

On Linux, its common signal number is:

```text
15
```

A process can catch `SIGTERM`, perform cleanup, and terminate normally.

Typical cleanup operations include:

* Stop accepting new work
* Disable hardware outputs
* Close files
* Flush log buffers
* Release resources
* Notify other components
* Exit normally

---

## 12. `SIGKILL`

`SIGKILL` forces immediate process termination.

It can be sent using:

```bash
kill -KILL PID
```

or:

```bash
kill -9 PID
```

On Linux, its signal number is:

```text
9
```

A process cannot install a handler for `SIGKILL`.

Therefore:

* No application handler runs
* No shutdown flag is set
* No userspace cleanup runs
* No final application message is printed

Observed output:

```text
Killed
```

This message was printed by the shell, not by the terminated application.

---

## 13. Signal Comparison

| Property             |                 `SIGINT` |          `SIGTERM` |               `SIGKILL` |
| -------------------- | -----------------------: | -----------------: | ----------------------: |
| Typical source       |                 `Ctrl+C` | Service or process | Administrator or kernel |
| Can be caught        |                      Yes |                Yes |                      No |
| Can be ignored       |                      Yes |                Yes |                      No |
| Can be blocked       |                      Yes |                Yes |                      No |
| Cleanup possible     |                      Yes |                Yes |                      No |
| Typical Linux number |                        2 |                 15 |                       9 |
| Intended use         | Interactive interruption |  Graceful shutdown |      Forced termination |

The recommended termination sequence is:

```text
1. Send SIGTERM.
2. Allow time for graceful shutdown.
3. Use SIGKILL only if the process does not respond.
```

## 14. The `signal()` Interface

The older interface is:

```c
signal(SIGTERM, terminationSignalHandler);
```

The handler prototype is:

```c
void handler(int signalNumber);
```

Although `signal()` is simple, modern POSIX applications normally prefer:

```c
sigaction()
```

`sigaction()` provides more explicit and consistent control over:

* Signal masks
* Optional flags
* Detailed signal information
* System-call restart behavior
* Previous signal disposition

---

## 15. The `sigaction()` Function

Prototype:

```c
int sigaction(
    int signalNumber,
    const struct sigaction *newAction,
    struct sigaction *oldAction);
```

Example:

```c
sigaction(SIGTERM, &action, NULL);
```

The parameters mean:

### `signalNumber`

The signal whose behavior will be configured.

```c
SIGTERM
```

### `newAction`

A pointer to the new signal configuration.

```c
&action
```

### `oldAction`

A pointer where the previous configuration can be stored.

Using:

```c
NULL
```

means that the previous configuration is not requested.

---

## 16. Initializing `struct sigaction`

The configuration structure can be created using:

```c
struct sigaction action = {0};
```

This initializes the structure fields to zero.

Initialization is important because the structure may contain multiple members and platform-specific internal fields.

Leaving fields uninitialized may cause undefined or unexpected behavior.

---

## 17. `sa_handler`

The basic signal handler is assigned using:

```c
action.sa_handler = terminationSignalHandler;
```

The handler prototype is:

```c
static void terminationSignalHandler(
    int signalNumber);
```

Example:

```c
static void terminationSignalHandler(
    int signalNumber)
{
    g_receivedSignal = signalNumber;
}
```

The kernel provides the received signal number.

The same handler can be installed for multiple signals:

```c
sigaction(SIGINT, &action, NULL);
sigaction(SIGTERM, &action, NULL);
```

The handler can then distinguish between:

```c
signalNumber == SIGINT
```

and:

```c
signalNumber == SIGTERM
```

---

## 18. `sa_sigaction`

A more detailed signal handler can be assigned using:

```c
action.sa_sigaction = detailedSignalHandler;
```

The handler prototype is:

```c
static void detailedSignalHandler(
    int signalNumber,
    siginfo_t *signalInfo,
    void *context);
```

This mode requires:

```c
action.sa_flags = SA_SIGINFO;
```

The `siginfo_t` structure may provide information such as:

* Sender PID
* Sender user ID
* Child exit status
* Signal origin
* Fault address
* Signal-specific event code

`sa_handler` and `sa_sigaction` should not be used simultaneously.

---

## 19. `sa_mask`

The `sa_mask` member defines additional signals that are blocked while the handler runs.

It is initialized using:

```c
sigemptyset(&action.sa_mask);
```

This creates an empty signal set.

The practical meaning is:

```text
Do not block any additional signals while the handler executes
```

The signal currently being handled is normally blocked automatically while its handler is running.

Additional signals can be added using:

```c
sigaddset(&action.sa_mask, SIGINT);
sigaddset(&action.sa_mask, SIGTERM);
```

This can prevent another termination handler from interrupting the current handler.

---

## 20. Why `sigemptyset()` Receives an Address

The call is:

```c
sigemptyset(&action.sa_mask);
```

The `&` operator provides the address of:

```c
action.sa_mask
```

The function needs the address because it modifies the signal-set object.

Return value:

```text
0  › Success
-1 › Failure
```

Robust error handling:

```c
if (sigemptyset(&action.sa_mask) != 0)
{
    perror("sigemptyset");
    return EXIT_FAILURE;
}
```

---

## 21. Installing the `SIGINT` Handler

The following code installs the prepared action for `SIGINT`:

```c
if (sigaction(SIGINT, &action, NULL) != 0)
{
    perror("sigaction SIGINT");
    return EXIT_FAILURE;
}
```

This means:

```text
Use the behavior stored in action when SIGINT is delivered
```

The previous `SIGINT` behavior is not requested because the third parameter is:

```c
NULL
```

---

## 22. Installing the `SIGTERM` Handler

The same action is installed for `SIGTERM`:

```c
if (sigaction(SIGTERM, &action, NULL) != 0)
{
    perror("sigaction SIGTERM");
    return EXIT_FAILURE;
}
```

Both signals therefore execute:

```c
terminationSignalHandler
```

The handler stores the signal number so the main loop can identify the shutdown reason.

---

## 23. `sa_flags`

The `sa_flags` member controls optional signal behavior.

The demo uses:

```c
action.sa_flags = 0;
```

This enables no optional flags.

Common flags include:

```text
SA_RESTART
SA_SIGINFO
SA_NODEFER
SA_RESETHAND
SA_NOCLDSTOP
SA_NOCLDWAIT
```

---

## 24. `SA_RESTART`

The flag:

```c
SA_RESTART
```

causes some interrupted blocking system calls to restart automatically after the signal handler returns.

Example blocking call:

```c
read(fileDescriptor, buffer, bufferSize);
```

Without `SA_RESTART`:

```text
Signal arrives
Handler runs
read() may return -1
errno may become EINTR
```

With `SA_RESTART`:

```text
Signal arrives
Handler runs
Kernel may restart read()
```

This is useful in some applications but may be undesirable during shutdown.

If the system call restarts automatically, the main loop may not immediately check the shutdown flag.

For this reason, the demo uses:

```c
action.sa_flags = 0;
```

---

## 25. `SA_NODEFER`

Normally, a signal is blocked while its own handler is running.

With:

```c
SA_NODEFER
```

the same signal may interrupt its own handler.

This can produce recursive signal-handler calls:

```text
Signal
  |
  +-- Handler
        |
        +-- Same signal
              |
              +-- Handler
```

This may cause stack overflow or uncontrolled behavior.

It is normally avoided unless there is a specific reason to use it.

---

## 26. `SA_RESETHAND`

With:

```c
SA_RESETHAND
```

the custom handler is reset to the default disposition after the first signal delivery.

Example behavior:

```text
First SIGINT  › Custom handler
Second SIGINT › Default action
```

This flag is used only in special designs.

---

## 27. `SA_NOCLDSTOP`

This flag is used with:

```text
SIGCHLD
```

A parent may receive `SIGCHLD` when a child:

* Terminates
* Stops
* Continues

Using:

```c
SA_NOCLDSTOP
```

prevents `SIGCHLD` delivery for child stop and continue events.

Termination events can still be reported.

---

## 28. `SA_NOCLDWAIT`

Using:

```c
SA_NOCLDWAIT
```

can prevent terminated children from becoming zombies.

The kernel may automatically discard their termination records.

However, this may prevent the parent from retrieving the child exit status using:

```c
waitpid();
```

It should only be used when the parent does not need the child result.

---

## 29. Signal Handler Execution Flow

When a signal is delivered, the kernel conceptually performs the following operations:

```text
1. Save the current execution context
2. Prepare the process to execute the handler
3. Run the handler
4. Return from the handler
5. Restore the previous execution context
6. Continue normal program execution
```

The execution context includes information such as:

* Program counter
* Registers
* Stack state
* Signal mask

The signal may arrive while the program is executing almost any instruction.

---

## 30. Why Signal Handlers Must Be Minimal

A signal may arrive while the program is:

* Executing `printf()`
* Allocating memory
* Releasing memory
* Holding a mutex
* Updating shared state
* Accessing a device
* Performing file I/O

Calling complex functions from the handler can create:

* Deadlocks
* Reentrancy problems
* Heap corruption
* Inconsistent application state
* Nested handler problems

Functions such as the following should generally not be used in an asynchronous signal handler:

```c
printf()
fprintf()
malloc()
free()
fopen()
pthread_mutex_lock()
```

The handler should normally perform only minimal, signal-safe operations.

---

## 31. `volatile sig_atomic_t`

The application stores the received signal in:

```c
static volatile sig_atomic_t g_receivedSignal = 0;
```

### `sig_atomic_t`

This integer type supports simple atomic reads and writes between:

* Normal application code
* An asynchronous signal handler

It is suitable for:

* Boolean signal flags
* Small signal numbers
* Basic shutdown requests

### `volatile`

The value may change outside the normal visible program flow.

The `volatile` keyword prevents the compiler from assuming that the value remains unchanged.

The main loop repeatedly checks the real value:

```c
while (g_receivedSignal == 0)
{
    /* Normal application work. */
}
```

---

## 32. Graceful Shutdown Pattern

The recommended simple design is:

```text
Signal handler:
    Store signal or set stop flag

Main application:
    Detect stop request
    Stop normal operations
    Disable outputs
    Close resources
    Exit normally
```

Example handler:

```c
static void terminationSignalHandler(
    int signalNumber)
{
    g_receivedSignal = signalNumber;
}
```

Example main loop:

```c
while (g_receivedSignal == 0)
{
    applicationUpdate();
}
```

Cleanup is then executed in normal program context:

```c
performCleanup();
```

---

## 33. Interrupted System Calls

A blocking system call may be interrupted by signal delivery.

Example:

```c
result = read(
    fileDescriptor,
    buffer,
    bufferSize);
```

When interrupted, the function may return:

```text
result = -1
errno = EINTR
```

`EINTR` means:

```text
Interrupted system call
```

---

## 34. Basic `EINTR` Retry Pattern

A common pattern is:

```c
do
{
    result = read(
        fileDescriptor,
        buffer,
        bufferSize);
}
while ((result < 0) &&
       (errno == EINTR));
```

This retries the operation when it is interrupted by a signal.

However, this pattern is not always the most robust solution.

If signals continue arriving, the operation may repeatedly restart without making progress.

This is closer to:

```text
Livelock or starvation
```

than a classic deadlock.

---

## 35. Robust `EINTR` Policy

A robust application should decide whether the operation should really be retried.

The decision may depend on:

* Whether shutdown was requested
* Whether the signal is informational
* Whether the operation has a deadline
* Whether a timeout has expired
* Whether a retry limit is appropriate
* Whether the operation can safely be repeated

Example policy:

```text
Temporary signal:
    Retry operation

Shutdown signal:
    Stop retrying
    Begin cleanup
```

A shutdown-aware loop may check:

```c
g_receivedSignal
```

before retrying.

---

## 36. Retry Count and Deadline

A fixed retry count can prevent unbounded retries:

```text
Retry at most three times
```

However, a fixed count is not always meaningful.

An absolute deadline is often more robust:

```text
The operation must finish within 500 ms
```

With a deadline:

* Signal interruptions are allowed
* Retries may continue
* The total permitted time remains bounded

This approach is useful in real-time and embedded systems.

---

## 37. Alternatives to Asynchronous Signal Handlers

More advanced designs include:

### `pselect()`

Waits for file-descriptor events while coordinating signal-mask changes.

### `ppoll()`

Provides similar behavior using poll-style file-descriptor monitoring.

### Self-Pipe Technique

The signal handler writes a byte to a pipe.

The main event loop detects the pipe as readable.

### `signalfd()`

Linux-specific interface that converts signals into file-descriptor events.

### `sigwait()`

Synchronously waits for blocked signals in normal execution context.

### Dedicated Signal Thread

One thread receives and processes signals for a multithread application.

These methods will be covered in later lessons.

## 43. Hardware Watchdog

A hardware watchdog is a timer that supervises software execution.

The application must periodically refresh the watchdog:

```text
Application healthy
        |
        +-- Refresh watchdog
        |
        +-- Watchdog timer restarts
```

If the application fails to refresh it:

```text
Application hangs
        |
        +-- Watchdog timeout expires
        |
        +-- Processor or system resets
```

A watchdog can detect problems such as:

* Infinite loops
* Deadlocks
* Scheduler failure
* Critical task failure
* Software lockup
* Missing control-loop execution

A robust system should refresh the watchdog only when all critical software components are healthy.

---

## 44. External Enable Line

An external enable line controls whether a power stage or actuator driver is active.

Example:

```text
ENABLE = 1 › Driver enabled
ENABLE = 0 › Driver disabled
```

The enable signal may be controlled by:

* Safety MCU
* FPGA
* Watchdog circuit
* Emergency-stop circuit
* Hardware interlock

A pull-down resistor can keep the driver disabled while the processor is:

* Powered off
* Resetting
* Booting
* Configuring GPIO pins

This prevents unintended actuator activation.

---

## 45. Failsafe PWM State

A failsafe PWM state defines the actuator behavior when the PWM signal:

* Stops updating
* Disappears
* Becomes invalid
* Exceeds valid limits

Possible failsafe behavior includes:

* Neutral command
* Stop command
* Minimum output
* Disabled output
* Driver enable low

The correct safe state depends on system-level safety analysis.

A neutral value is not automatically safe for every actuator.

---

## 46. Communication Timeout

An actuator should not apply the last command forever when communication is lost.

The receiver monitors the age of the latest valid command.

Example:

```text
Last command received: 10.000 s
Current time:          10.250 s
Timeout limit:          0.200 s
```

Because the command is too old:

```text
Command becomes invalid
Output enters safe state
```

Timeout selection must balance:

* Fast fault reaction
* Communication jitter tolerance
* Network delays
* Control-loop timing
* System dynamics

---

## 47. Independent Safety Controller

An independent safety controller validates the main processor's outputs.

Example architecture:

```text
Linux processor
      |
      +-- High-level command
      |
Safety MCU or FPGA
      |
      +-- Range checks
      +-- Rate checks
      +-- Timeout checks
      +-- Sensor plausibility
      +-- Heartbeat monitoring
      +-- Final enable control
      |
Actuator
```

The safety controller may:

* Reject invalid commands
* Limit command rates
* Disable outputs
* Select a safe command
* Request system reset

Independence may require:

* Separate clock
* Separate reset
* Separate power supply
* Separate software
* Separate requirements
* Independent monitoring inputs

---

## 48. Power-On Default Safe Output

A Linux application does not start immediately after power is applied.

The startup sequence may include:

```text
Power applied
Boot ROM
Bootloader
Linux kernel
Drivers
Userspace services
Application startup
```

Outputs must remain safe during the entire startup period.

Safety methods include:

* Pull-down on enable pins
* Driver default-off behavior
* Timer output reset state
* Hardware gating
* Safety relay
* Delayed power-stage enable
* Application self-test before activation

The output should only be enabled after:

```text
Boot completed
Sensors valid
Communication valid
Self-test passed
Safety conditions satisfied
```

---

## 49. Layered Safety Design

Signal handling is only one layer of a safe embedded Linux design.

A layered example is:

```text
Power-on:
    Enable defaults to LOW

Normal operation:
    Communication timeout monitored
    PWM updated
    Watchdog refreshed

Communication failure:
    Failsafe output selected

Application hang:
    Watchdog resets system

Invalid command:
    Safety controller rejects command

Emergency stop:
    Hardware enable becomes LOW
```

The main principle is:

```text
Do not rely on a single software mechanism
```

## 50. Key Takeaways

* A signal is an asynchronous process notification.
* Signals may come from the kernel, terminal, or another process.
* `kill()` sends signals and does not always kill the target.
* `SIGINT` is commonly generated by `Ctrl+C`.
* `SIGTERM` requests graceful termination.
* `SIGKILL` forces immediate termination.
* `SIGKILL` cannot be caught, ignored, or blocked.
* `sigaction()` provides controlled signal configuration.
* `sa_handler` defines a basic handler.
* `sa_sigaction` provides extended signal information.
* `sa_mask` defines signals blocked during handler execution.
* `sa_flags` controls optional signal behavior.
* `SA_RESTART` may restart interrupted system calls.
* Signal handlers should perform minimal work.
* Cleanup should run in normal application context.
* `volatile sig_atomic_t` is suitable for a simple signal flag.
* A system call interrupted by a signal may return `EINTR`.
* Blindly retrying on `EINTR` may prevent forward progress.
* Robust systems use shutdown checks, deadlines, or event-driven interfaces.
* POSIX feature-test macros may be required for `sigaction()`.
* Graceful shutdown does not replace hardware safety mechanisms.
* Hardware watchdogs, enable lines, failsafe outputs, timeouts, and safety controllers provide additional protection.
