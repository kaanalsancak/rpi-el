# Lesson 002 — Process Lifecycle and Signals

## 1. Lesson Overview

This lesson covers Linux process synchronization, child process termination, zombie processes, and signal handling.

The practical examples demonstrate:

* Waiting for a specific child process with `waitpid()`
* Reading a child process exit status
* Creating and observing a zombie process
* Installing signal handlers with `sigaction()`
* Handling `SIGINT` and `SIGTERM`
* Observing the behavior of `SIGKILL`
* Performing graceful application shutdown

The following applications were created:

```text
apps/process_wait_demo
apps/process_zombie_demo
apps/process_signal_demo
```

## 2. Waiting for a Child Process

When a parent process creates a child using `fork()`, the parent may need to wait until the child terminates.

The `waitpid()` system call can be used to wait for a specific child process.

```c
pid_t waitpid(
    pid_t pid,
    int *status,
    int options);
```

Example:

```c
terminatedProcessId = waitpid(childProcessId, &childStatus, 0);
```

The parameters have the following meanings:

* `childProcessId` identifies the child process to wait for.
* `childStatus` receives encoded termination information.
* `0` causes the call to block until the child terminates.

The return value is:

* The PID of the terminated child on success
* `-1` on failure

---

## 3. Child Exit Status

A child process may terminate with an exit status:

```c
exit(42);
```

The parent does not read the value directly from the status variable. The status contains encoded process information.

The following macros are used:

### `WIFEXITED`

Checks whether the child terminated normally.

```c
if (WIFEXITED(childStatus))
{
    /* The child terminated normally. */
}
```

### `WEXITSTATUS`

Returns the normal exit status of the child.

```c
int exitStatus = WEXITSTATUS(childStatus);
```

For a child that calls:

```c
exit(42);
```

the extracted exit status is:

```text
42
```

### `WIFSIGNALED`

Checks whether the child was terminated by a signal.

```c
if (WIFSIGNALED(childStatus))
{
    /* The child was terminated by a signal. */
}
```

### `WTERMSIG`

Returns the signal that terminated the child.

```c
int terminatingSignal = WTERMSIG(childStatus);
```

## 4. Zombie Processes

A zombie process is a child process that has finished executing but has not yet been collected by its parent.

The lifecycle is:

```text
Parent calls fork()
        |
        +-- Child runs
        |
        +-- Child calls exit()
        |
        +-- Child becomes a zombie
        |
        +-- Parent calls wait() or waitpid()
        |
        +-- Zombie entry is removed
```

A zombie process:

* Does not execute program instructions
* Does not consume CPU time
* Keeps a small process-table entry
* Keeps its PID and exit status
* Remains until its parent collects it

The zombie process was observed with:

```bash
ps -o pid,ppid,stat,state,cmd -p CHILD_PID
```

Example output:

```text
PID    PPID STAT S CMD
1858   1857 Z+   Z [process_zombie_] <defunct>
```

The important fields are:

* `Z` indicates the zombie state.
* `<defunct>` indicates that execution has finished.
* `PPID` identifies the parent that must collect the child.

After the parent calls `waitpid()`, the child entry disappears from the process table.

## 5. Signal Fundamentals

A signal is an asynchronous notification delivered to a process.

Signals may be generated by:

* The Linux kernel
* The terminal driver
* Another process
* The process itself
* Hardware or software faults

Examples include:

```text
SIGINT   — Interactive interrupt
SIGTERM  — Termination request
SIGKILL  — Forced process termination
SIGCHLD  — Child process state change
SIGSEGV  — Invalid memory access
```

A signal is mainly an event notification mechanism. It is not a general-purpose data communication mechanism.

---

## 6. The `kill()` Function

Despite its name, `kill()` does not always kill a process.

Its purpose is to send a signal.

```c
int kill(pid_t pid, int signalNumber);
```

Example:

```c
kill(targetProcessId, SIGTERM);
```

This asks the kernel to send `SIGTERM` to the target process.

The shell command:

```bash
kill -TERM PID
```

performs the same type of operation.

The default signal used by the `kill` command is `SIGTERM`.

```bash
kill PID
```

is equivalent to:

```bash
kill -TERM PID
```

---

## 7. `SIGINT`

`SIGINT` is normally generated when the user presses:

```text
Ctrl+C
```

The terminal driver sends `SIGINT` to the foreground process group.

Its default behavior is to terminate the process.

However, a process may install a handler and perform a graceful shutdown.

Observed application behavior:

```text
Ctrl+C
   |
   +-- SIGINT is generated
   |
   +-- The registered handler runs
   |
   +-- The shutdown flag is set
   |
   +-- The main loop terminates
   |
   +-- Cleanup is performed
```

On Linux, `SIGINT` normally has signal number:

```text
2
```

Application output:

```text
[APPLICATION] Received signal: SIGINT (2)
[APPLICATION] Cleanup completed.
[APPLICATION] Process terminating normally.
```

---

## 8. `SIGTERM`

`SIGTERM` is the standard request for controlled process termination.

It can be sent using:

```bash
kill -TERM PID
```

It may also be written as:

```bash
kill -15 PID
```

The symbolic form is preferred because it is more readable.

A process can:

* Catch `SIGTERM`
* Ignore `SIGTERM`
* Temporarily block `SIGTERM`
* Perform cleanup before exiting

Typical graceful shutdown operations include:

```text
Stop accepting new commands
Disable application outputs
Close files and devices
Release allocated resources
Flush log buffers
Terminate normally
```

Observed application output:

```text
[APPLICATION] Received signal: SIGTERM (15)
[APPLICATION] Stopping normal operations.
[APPLICATION] Disabling simulated outputs.
[APPLICATION] Closing simulated resources.
[APPLICATION] Cleanup completed.
[APPLICATION] Process terminating normally.
```

---

## 9. `SIGKILL`

`SIGKILL` immediately terminates a process.

It can be sent using:

```bash
kill -KILL PID
```

or:

```bash
kill -9 PID
```

Unlike `SIGINT` and `SIGTERM`, `SIGKILL`:

* Cannot be caught
* Cannot be ignored
* Cannot be blocked
* Cannot have a signal handler
* Does not allow userspace cleanup

Observed output:

```text
Killed
```

The application did not print cleanup messages because the kernel terminated it directly.

The `Killed` message was printed by the shell, not by the terminated application.

---

## 10. `SIGTERM` and `SIGKILL` Comparison

| Property              |            `SIGTERM` |          `SIGKILL` |
| --------------------- | -------------------: | -----------------: |
| Can be caught         |                  Yes |                 No |
| Can be ignored        |                  Yes |                 No |
| Can be blocked        |                  Yes |                 No |
| Handler can run       |                  Yes |                 No |
| Cleanup can run       |                  Yes |                 No |
| Default signal number |                   15 |                  9 |
| Intended purpose      | Graceful termination | Forced termination |

The recommended shutdown sequence is:

```text
1. Send SIGTERM.
2. Allow the process to shut down safely.
3. Use SIGKILL only when the process does not respond.
```

## 11. Installing Handlers with `sigaction()`

The `sigaction()` function defines how a process handles a signal.

```c
int sigaction(
    int signalNumber,
    const struct sigaction *newAction,
    struct sigaction *oldAction);
```

Example:

```c
sigaction(SIGTERM, &action, NULL);
```

This means:

```text
Install the behavior stored in action for SIGTERM.
Do not return the previous behavior.
```

A signal action structure was prepared as follows:

```c
struct sigaction action = {0};

action.sa_handler = terminationSignalHandler;
action.sa_flags = 0;
```

---

## 12. `sa_handler`

The `sa_handler` member stores the handler function.

```c
action.sa_handler = terminationSignalHandler;
```

The handler has the following prototype:

```c
static void terminationSignalHandler(int signalNumber);
```

The kernel passes the received signal number to the handler.

The same handler can be installed for multiple signals:

```c
sigaction(SIGINT, &action, NULL);
sigaction(SIGTERM, &action, NULL);
```

Inside the handler:

```c
static void terminationSignalHandler(int signalNumber)
{
    g_receivedSignal = signalNumber;
}
```

The stored value identifies whether `SIGINT` or `SIGTERM` was received.

---

## 13. `sa_mask`

The `sa_mask` member defines additional signals that should be blocked while the handler is running.

It was initialized using:

```c
sigemptyset(&action.sa_mask);
```

This creates an empty signal set.

In this application, it means:

```text
Do not block any additional signals while the handler runs.
```

The signal currently being handled is normally blocked automatically while its handler is running.

Additional signals could be added using:

```c
sigaddset(&action.sa_mask, SIGINT);
sigaddset(&action.sa_mask, SIGTERM);
```

---

## 14. `sa_flags`

The `sa_flags` member controls additional signal behavior.

The demo uses:

```c
action.sa_flags = 0;
```

This means no optional behavior flags are enabled.

A commonly used flag is:

```c
SA_RESTART
```

`SA_RESTART` causes some interrupted system calls to restart automatically after the signal handler returns.

However, it is not always desirable during shutdown. A blocking system call may restart and prevent the main loop from checking the shutdown flag immediately.

For this lesson, `SA_RESTART` was intentionally not enabled.

## 15. Signal Handler Safety

A signal handler may run at almost any point in the program.

For example, a signal may arrive while the application is:

* Printing output
* Allocating memory
* Updating global data
* Holding a lock
* Performing file I/O
* Waiting inside a system call

For this reason, a handler should remain short and simple.

Functions such as the following should generally not be called from an asynchronous signal handler:

```c
printf()
malloc()
free()
fopen()
pthread_mutex_lock()
```

The demo handler only stores the received signal:

```c
static volatile sig_atomic_t g_receivedSignal = 0;

static void terminationSignalHandler(int signalNumber)
{
    g_receivedSignal = signalNumber;
}
```

Cleanup is performed later in normal program context.

---

## 16. `volatile sig_atomic_t`

The global signal variable was declared as:

```c
static volatile sig_atomic_t g_receivedSignal = 0;
```

### `sig_atomic_t`

`sig_atomic_t` is an integer type suitable for simple atomic access between normal code and a signal handler.

It is appropriate for storing a basic signal flag or signal number.

### `volatile`

`volatile` tells the compiler that the value may change outside the normal program flow.

The main loop must therefore read the variable again instead of assuming it remains unchanged.

```c
while (g_receivedSignal == 0)
{
    /* Normal application work. */
}
```

The variable may be changed asynchronously by the signal handler.

---

## 17. Graceful Shutdown Design

The application uses the following design:

```text
Signal handler:
    Store the received signal number

Main loop:
    Check the signal variable
    Stop normal operations
    Perform cleanup
    Terminate normally
```

This separates asynchronous signal handling from normal application cleanup.

The handler does not:

* Print messages
* Close resources
* Disable outputs
* Allocate or release memory

Those operations are performed after the main loop detects the signal.

## 18. Interrupted System Calls and `EINTR`

A blocking system call may be interrupted by a signal.

Example:

```c
result = read(fileDescriptor, buffer, bufferSize);
```

If the call is interrupted, it may return:

```text
result = -1
errno = EINTR
```

A simple retry pattern is:

```c
do
{
    result = read(fileDescriptor, buffer, bufferSize);
}
while ((result < 0) && (errno == EINTR));
```

However, blindly retrying forever is not always robust.

If the signal requests shutdown, the application should normally stop retrying and begin cleanup.

A more robust policy should consider:

* Whether shutdown was requested
* Whether the operation has a timeout
* Whether a retry limit is required
* Whether an absolute deadline has expired
* Whether an event-driven API should be used

More advanced alternatives include:

```text
pselect()
ppoll()
signalfd()
self-pipe
sigwait()
dedicated signal thread
```

These mechanisms will be covered in later lessons.

## 19. POSIX Feature-Test Macro

`sigaction()`, `sigemptyset()`, and `struct sigaction` are POSIX interfaces.

The build configuration enables POSIX.1-2008 declarations:

```cmake
target_compile_definitions(process_signal_demo PRIVATE
    _POSIX_C_SOURCE=200809L
)
```

Without this definition, strict C compilation may hide the POSIX declarations and produce errors such as:

```text
storage size of ‘action’ is not known
implicit declaration of function ‘sigemptyset’
implicit declaration of function ‘sigaction’
```

The definition informs the system headers that POSIX.1-2008 APIs should be exposed.

## 20. Embedded Linux Safety Considerations

Graceful signal handling is useful, but it is not sufficient for safety-critical output control.

A process may:

* Crash
* Deadlock
* Receive `SIGKILL`
* Stop being scheduled
* Experience a kernel failure
* Lose electrical power

Additional safety mechanisms may include:

### Hardware Watchdog

A hardware timer resets the processor or system when software fails to provide a periodic health indication.

### External Enable Line

A separate hardware signal enables or disables the actuator power stage.

A pull-down resistor can keep the output disabled during boot or reset.

### Failsafe PWM State

The actuator or driver enters a defined safe state when PWM updates stop or the input becomes invalid.

### Communication Timeout

The receiver invalidates stale commands when valid messages are not received within a defined time.

### Independent Safety Controller

A separate MCU, FPGA, or hardware circuit validates commands and controls the final actuator enable path.

### Power-On Default Safe Output

Outputs remain disabled or in a safe electrical state before the operating system and application finish starting.

These mechanisms create multiple independent safety layers.

## 22. Key Takeaways

* `waitpid()` waits for a specific child process.
* Child termination information is encoded in the status value.
* `WIFEXITED()` checks for normal termination.
* `WEXITSTATUS()` extracts the child exit status.
* A zombie is a terminated child that has not been collected.
* `wait()` or `waitpid()` removes the zombie entry.
* A signal is an asynchronous process notification.
* `kill()` sends a signal and does not necessarily kill a process.
* `SIGINT` is commonly generated by `Ctrl+C`.
* `SIGTERM` requests graceful termination.
* `SIGKILL` forces immediate termination.
* `SIGKILL` cannot be caught, ignored, or blocked.
* `sigaction()` is preferred over the older `signal()` interface.
* Signal handlers should perform minimal work.
* Cleanup should be performed in normal application context.
* `volatile sig_atomic_t` is suitable for a simple signal flag.
* Userspace signal handling is not a replacement for hardware safety mechanisms.
